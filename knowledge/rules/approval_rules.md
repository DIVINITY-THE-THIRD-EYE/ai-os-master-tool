# AI OS v4 Multi-Agent Approval Rules (`approval_rules.md`)

## 1. Overview & Approval Gate Framework

Approval rules define the verification gates, signature quorums, risk thresholds, and authorization steps required before executing high-impact state transitions (e.g., architecture changes, schema alterations, production deployments, or budget increases).

---

## 2. Approval Rule Specifications

### Rule APP-001: Risk-Weighted Approval Matrix
- **Rule ID**: `APP-001`
- **Severity**: `CRITICAL`
- **Scope**: Approval Engine & Quality Gates
- **Description**: Operational actions are assigned a Risk Category (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`). Approval requirements scale proportionally with calculated risk.
- **Approval Requirements Matrix**:
  | Risk Category | Example Action | Quorum Required | Authorized Roles | Timeout SLA |
  |---|---|---|---|---|
  | `LOW` | Documentation fix, unit test update | 1 Signature | Primary Agent | 5 minutes |
  | `MEDIUM` | Non-breaking API edit, lint refactor | 2 Signatures | Primary Agent + QA (A06) | 30 minutes |
  | `HIGH` | DB migration, new dependency addition | 3 Signatures | Architect (A03) + Lead Eng (A04) + QA (A06) | 2 hours |
  | `CRITICAL` | Prod release, security policy bypass | 3 Signatures + Human | Master (A01) + Security (A07) + Lead + Human | 24 hours |

### Rule APP-002: Multi-Signature Quorum Standards
- **Rule ID**: `APP-002`
- **Severity**: `CRITICAL`
- **Scope**: Gate Evaluation Engine
- **Description**: For actions requiring multi-signature approval ($M$-of-$N$ quorum), no single agent or human operator may sign on behalf of multiple required roles (Enforcement of Separation of Duties).

### Rule APP-003: Mandatory Cryptographic Signature Format
- **Rule ID**: `APP-003`
- **Severity**: `CRITICAL`
- **Scope**: Approval Tokens & Certificates
- **Description**: Approval tokens must contain a signed JWT or Ed25519 cryptographic payload containing payload hash, approver role, timestamp, and expiration.
- **Approval Payload Schema**:
  ```json
  {
    "approval_id": "APPR-2026-00492",
    "gate_id": "GATE_PROD_DEPLOY",
    "target_artifact_sha256": "4b2a8f...90c1",
    "approver_id": "A07",
    "approver_role": "SecurityAuditor",
    "decision": "APPROVED",
    "expires_at": "2026-08-06T17:35:26Z",
    "signature": "MEQCID...Ed25519_sig"
  }
  ```

### Rule APP-004: Approval Gate Expiration & Automated Revocation
- **Rule ID**: `APP-004`
- **Severity**: `HIGH`
- **Scope**: Approval Token Lifecycle
- **Description**: Approval tokens expire automatically if the underlying state or target artifact hash changes after approval issuance. Any modification to a pre-approved artifact invalidates the prior signature.

### Rule APP-005: Fast-Track Emergency Approval Bypass (P0 Protocol)
- **Rule ID**: `APP-005`
- **Severity**: `CRITICAL`
- **Scope**: Emergency Production Patching
- **Description**: In a `P0_CRITICAL` emergency incident, the human operator or Master Orchestrator (A01) can issue an `EMERGENCY_OVERRIDE_TOKEN`.
- **Post-Bypass Requirement**: Retrospective multi-agent audit sign-off MUST be completed within 12 hours of emergency deployment.

### Rule APP-006: Delegation & Proxy Approval Rules
- **Rule ID**: `APP-006`
- **Severity**: `MEDIUM`
- **Scope**: Agent Delegation Engine
- **Description**: An agent may delegate its approval authority to an explicit alternate agent (e.g., A04 delegates to A03 during maintenance windows) only if an active `DELEGATION_POLICY` record is logged in the knowledge graph.

### Rule APP-007: Non-Repudiation Guarantee
- **Rule ID**: `APP-007`
- **Severity**: `HIGH`
- **Scope**: Audit Subsystem
- **Description**: All approval decisions (both `APPROVED` and `REJECTED`) are appended to the immutable WORM audit log. Approvers cannot revoke or erase past approval records.

### Rule APP-008: Mandatory Rejection Reason Specifications
- **Rule ID**: `APP-008`
- **Severity**: `HIGH`
- **Scope**: Rejection Feedback Handling
- **Description**: If an approver issues a `REJECTED` decision, the decision payload MUST include structured rejection reasons referencing specific failed rules (e.g., `REJECTED: Failed SEC-001 - Hardcoded key found at line 42`).

### Rule APP-009: Automated Approval Decision Engine Integration
- **Rule ID**: `APP-009`
- **Severity**: `HIGH`
- **Scope**: Decision Engine (Phase 7)
- **Description**: Automated approval decisions generated by AI agents must evaluate rule predicates against deterministic rule engines (`rego` / `cel`) rather than unconstrained LLM text generation.

### Rule APP-010: Conflict of Interest Self-Approval Prohibition
- **Rule ID**: `APP-010`
- **Severity**: `CRITICAL`
- **Scope**: All Agents & Humans
- **Description**: The agent or author that generated an artifact CANNOT serve as an approving authority for that same artifact (`Self-Approval Prohibition`).
